# Releasing Semantta

This document describes the process for building, validating, and publishing a Semantta release.

## Release model

Semantta releases are created from Git tags using the following format:

```text
vMAJOR.MINOR.PATCH
```

For example:

```text
v0.1.0
v0.2.0
v1.0.0
```

The Git tag is the source of truth for the release version. The GitHub Actions workflow applies the tag version to the packaged application during the release build.

## Supported release packages

The current release pipeline produces:

| Platform | Architecture | Package                 |
| -------- | ------------ | ----------------------- |
| Linux    | x64          | AppImage                |
| Linux    | x64          | Debian package (`.deb`) |
| Windows  | x64          | NSIS installer (`.exe`) |
| macOS    | arm64        | DMG                     |
| macOS    | arm64        | ZIP                     |
| macOS    | x64          | DMG                     |
| macOS    | x64          | ZIP                     |

Linux distribution through APT and Arch/Pacman repositories is planned separately and is not yet part of the release pipeline.

## Before creating a release

Ensure that:

1. The intended changes are merged into `main`.
2. The working tree is clean.
3. The application version being released is known.
4. The GitHub Actions build and test workflow is ready to run successfully.

The workflow performs the following release checks automatically:

* dependency installation and caching
* backend packaging
* bundled runtime preparation
* frontend generation
* Electron packaging
* packaged-application smoke testing
* user-data preservation testing
* installer/package verification
* release artifact verification
* SHA-256 checksum generation

## Creating a release

Create and push a version tag:

```bash
git tag v0.1.0
git push origin v0.1.0
```

GitHub Actions detects the `v*` tag and performs the release build.

The workflow validates the tag as a SemVer-compatible version before applying it to the application package.

## Release pipeline

For a release tag, the workflow performs:

```text
Version tag
    ↓
Build all supported platforms
    ↓
Smoke tests
    ↓
User-data preservation tests
    ↓
Installer/package tests
    ↓
Build artifact verification
    ↓
Upload CI build artifacts
    ↓
Create GitHub Release
    ↓
Publish 7 distributable packages
    ↓
Publish SHA256SUMS
    ↓
Verify published release
    ↓
Verify published SHA-256 digests
```

A release is not created when a platform build or verification step fails.

## Release assets

Each release contains seven distributable files:

* Linux AppImage
* Linux Debian package
* Windows installer
* macOS arm64 DMG
* macOS arm64 ZIP
* macOS x64 DMG
* macOS x64 ZIP

The release also contains:

```text
SHA256SUMS
```

which contains SHA-256 checksums for the seven distributable packages.

## Verifying a downloaded package

Download the appropriate package and the `SHA256SUMS` file from the GitHub Release.

On Linux:

```bash
sha256sum -c SHA256SUMS
```

On macOS:

```bash
shasum -a 256 -c SHA256SUMS
```

On Windows PowerShell:

```powershell
Get-FileHash .\Semantta-<version>-win-x64.exe -Algorithm SHA256
```

Compare the resulting hash with the corresponding value in `SHA256SUMS`.

## Current signing status

The current Semantta release packages are not code-signed.

Windows code signing is intentionally deferred until a suitable open-source signing solution is available.

macOS Developer ID signing and notarization are also deferred.

Linux package-manager repository signing will be implemented when APT and Arch/Pacman distribution is added.

These decisions do not prevent the current release pipeline from building and publishing the packages.

## Data preservation

Semantta stores user data outside the application installation directory.

User data includes, where applicable:

* ontologies
* metadata
* cache
* plugins
* themes
* configuration and preferences
* logs
* Fuseki/TDB2 database data

Application updates must not remove this data.

The CI pipeline includes an automated data-preservation test for packaged applications.

## Release troubleshooting

If a release workflow fails:

1. Inspect the failing platform job.
2. Fix the underlying build or packaging problem.
3. Push the fix to `main`.
4. Create a new release tag.

Do not manually modify the release artifacts generated by the workflow.

When a release already exists and the workflow is rerun for the same tag, the release job updates the existing release assets.

## Future distribution

The planned Linux distribution channels are:

* Debian/Ubuntu through an APT repository
* Arch Linux through a Pacman-compatible repository

Package/repository signing will be implemented as part of that work.

Windows code signing and macOS signing/notarization may be added independently later.
